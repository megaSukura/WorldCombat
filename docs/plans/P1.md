**状态：已完成；后台检查及核心、完整组合客户端人工验收通过（2026-09-13）。** 实际范围见 [P1 检查记录](../development/P1-checks.md)。

依据：[完整计划的 P1 与工作包](../../cobblemon_world_combat_plan_v0.3.md#sec-15)、[P0 检查结果](../development/P0-checks.md)、[锁定版本的接入判断](../architecture/cobblemon-integration.md)。

## 目标与交付

P1 要证明两条路径实际可运行：

- **仅核心与通用前置：** 使用原版实体执行一个脚本动作，完成命中、结算和实例清理。
- **完整组合：** 放出伙伴 → 通过开发命令施法 → 命中野生目标并结算伤害，击败时结算一次经验 → 收回伙伴并释放相关实例。

交付两个 Mod、可编译运行的示例脚本、随实际接口维护的精简类型声明，以及启动／操作短说明和实际检查结果。示例采用有施法延迟和路径碰撞的投射动作，配合基础粒子与结果提示，让执行过程可观察。

## 实施顺序

| 编号 | 工作 | 可审查的结果 |
| --- | --- | --- |
| P1.1 | 接管旧战斗启动边界 | 在创建旧对局之前统一拒绝启动，覆盖跳过取消事件的调用及启动预热；招式、道具等数据仍正常初始化。优先评估限定到锁定方法的 Mixin，拒绝结果遵守上游调用合同。 |
| P1.2 | 建立核心动作与生命周期 | 服务端校验并推进动作；行动者句柄能区分实体离场与重新进入。定时任务、临时订阅和效果归属到实例，支持完成、取消、异常和离场清理，并设基础工作量上限。 |
| P1.3 | 接入最小双层脚本 SDK | 核心开放示例所需的通用能力，适配扩展伙伴身份和领域结算。接通 TypeScript 到 KubeJS 可执行 JS 的构建，实测回调、对象转换、参数错误和错误源位置。类型声明随可用接口增量维护。 |
| P1.4 | 接入个体状态与成长 | 以伙伴 UUID 关联当前活动实体，统一野生与有主个体的生命尺度和伤害处理；复用原有成长入口，明确经验归属并防止重复奖励。验证本路径涉及的生命、经验保存与再次读取。 |
| P1.5 | 串联示例并交付验证 | 同一通用动作经两种环境运行，脚本负责动作过程与数值，宿主负责受校验的世界操作。用少量开发命令触发和查看结果，完成相关检查后提供可运行产物及短清单。 |

先处理 P1.1 中已知的启动问题，再以核心示例推进运行时与 SDK，随后接入伙伴结算。出现能力缺口时补充可复用接口，具体实现以代码为准。

## 本阶段的关键约定

- **服务端决定结果。** 校验动作来源、控制权、目标有效性和作用范围。投射从行动者位置出发，按实际路径处理障碍与命中。
- **结算有明确归属。** 核心拥有瞬态动作；适配负责宝可梦生命与经验写入，复用原有同步、倒下及成长副作用。玩家和环境伤害与脚本伤害使用一致的生命换算策略。
- **先验证一种资源语义。** 开发动作使用可配置冷却，在动作提交时生效；提交前取消不消耗，提交后按动作规则结束，收回再放出仍保留尚未到期的冷却。原招式身份与 PP 继续由 Cobblemon 管理，正式招式的资源转译随内容接入确定。
- **离场以确认结果为准。** 收回被取消时保持有效绑定；实际收回、倒下、实体卸载、换维度或控制玩家离线时，结束受影响的动作。重新放出后，旧句柄及回调失效。
- **重载有清晰边界。** 脚本重载先暂停接收动作、释放瞬态实例，验证新内容后恢复；失败时报告不可用内容与原因。P1 的进行中动作在服务器停止时结束，生命与经验沿用 Cobblemon 存储。

P1 先完成这条路径所需的 SDK、成长与保存检查。正式快捷键、精确指令、HUD 和伙伴自主行为进入 P2；捕捉及其他成长条件随功能接入补齐。招式清单继续采用 P0 的轻量方式，类型工具和诊断能力按示例需要建设。

## 验证与桌面使用安排

Codex 负责实现和技术检查；用户审阅计划，并确认可见测试的时机。验证按下表执行：

| 范围 | 检查重点 |
| --- | --- |
| 构建与脚本 | 两个产物可构建，类型与编译后的脚本可用；错误能定位到内容来源，核心保持独立加载。 |
| 后台运行 | 在独立测试目录启动核心与完整组合专服，显式关闭专服 GUI 并隐藏启动窗口；检查数据初始化、脚本执行和正常停止。 |
| 旧入口 | 按接入记录检查固定组合中的默认挑战、NPC／MoLang、命令和直接启动调用；实际验证预热及跳过取消事件的路径也受约束。 |
| 结算与清理 | 命中及击败各结算一次；重复回调、失效目标、取消和收回不重复结算。抽取代表场景检查脚本异常、离场、重载后的实例／任务／订阅计数归位，并检查生命与经验保存读取。 |
| 可见客户端 | 在核心与完整组合中确认示例运行、反馈及收回结果；在客户端执行所需的实际入口触发检查，记录实际完成范围。 |

规则清晰的关键逻辑使用少量自动检查，世界行为使用代表场景验证。日志保留实例关联与必要计数；验证工具以当前检查可执行为准。

**会弹出游戏窗口、抢占前台或操作键鼠的测试，先说明内容、预计窗口数量与时长、是否需要人工操作，获得确认后再执行。** 阶段计划通过后，按这一约定另行安排可见测试，详见[项目协作规则](../../AGENTS.md)。等待合适时机时，继续不依赖该测试的工作，并将其标记为待验证。

## 完成条件与下一步

1. 核心独立运行示例，完整组合跑通放出、施法、伤害／经验结算和收回。
2. 固定支持组合中的已知旧战斗入口及预热路径受控，所需数据正常加载。
3. 当前路径通过一次结算、对象失效、清理及相关保存检查。
4. 交付物有可执行的短说明；检查记录区分已通过、待用户确认时机和待后续功能接入的项目。

完成后提交 P1 实施结果，再按“先计划、后审阅”的方式推进 P2。等待可见检查期间，如实保留待验状态，继续当前阶段不依赖该结果的工作。
