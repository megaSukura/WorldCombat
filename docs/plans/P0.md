# P0 执行计划：版本、范围与双 Mod 工程基线

**2026-09-13：已按用户审阅意见完成 P0，结果见[P0 检查记录](../development/P0-checks.md)。P0.3 采用轻量快照，分类与工具随内容开发需要增加。**

依据：[完整计划 v0.3](../../cobblemon_world_combat_plan_v0.3.md) 与[项目协作规则](../../AGENTS.md)。

## 目标与交付

锁定开发版本组合，构建两个独立 Mod，验证核心独立加载及完整组合的客户端／专服加载。形成 P1 所需的接入判断、招式范围说明与可调整的输入参考参数。

核心负责通用战斗能力；适配依赖核心与 Cobblemon，负责伙伴、成长、战斗接管及输入／UI。P0 交付工程基础，P1 接入放出—施法—结算—收回、脚本执行与旧战斗封锁，P2 形成实际操作样机。

## 实施任务

| 顺序 | 工作 | 完成依据 |
| --- | --- | --- |
| P0.1／W01 | 核对并锁定 MC、NeoForge、Java、Gradle、构建插件、Cobblemon、KubeJS、Rhino、Kotlin 与必要前置 | 构建直接读取固定版本配置；来源可定位，声明核对、构建和真实启动状态分别记录 |

| P0.3／W02 | 轻量记录锁定版本的招式数据来源与范围；容易取得时保留标识快照 | 来源、范围规则和待确认特殊机制明确；专用导出工具、全量可获得性分析与逐招进度系统按后续内容开发需要增加 |
| P0.4／W03 前置 | 调查个体身份、生命与成长写入、放出／收回和旧战斗入口 | P1 的接入选择、主要副作用和待实测项明确，说明链接到锁定源码 |
| P0.5 | 保存适配玩法原型参考配置与输入状态约定 | 数值集中在配置；责任边界、取消及服务端判定原则有简短说明，手感在 P2 人工试玩 |
| P0.6／T00 工程部分 | 构建、加载、依赖错误及文件检查，更新当前进度 | 记录实际命令／操作、结果和仍待执行项，提供必要启动步骤 |

P0.3 沿用的范围原则是“锁定 Cobblemon 默认数据与本项目明确启用规则下，可学习、获得或在战斗中产生的全部招式”。特殊系统和调用产生的招式随接入分类，完整覆盖仍是后续内容目标。P0 优先完成工程，轻量清单足以承接后续工作。

版本候选不可用时，在相同 MC／加载器路线内选择有来源依据的组合并记录差异；涉及平台或脚本宿主方向变化时，再提供具体替代建议。

## 检查与分工

Codex 完成构建、依赖和源码调查，并执行当前环境支持的真实加载检查：

- 核心与必要通用前置：客户端、专用服务器。
- 核心＋Cobblemon＋适配及全部前置：客户端、专用服务器。
- 缺失或不匹配的适配依赖：加载器应给出明确错误，同类元数据规则复用检查。
- 文件与清单：核对实际来源、内容、路径及文档链接。

用户或指定测试者负责实际操作、手感、可读性与玩法体验，P2 有样机后集中交接。真实启动条件暂缺时记录待办并提供短清单，继续独立的技术工作。

## 完成判定

两个 jar 可构建、依赖可复现、轻量范围说明及 P1 接入建议齐备，且适用的加载检查已有实际结果、关键加载问题已解决，即完成 P0。阶段结果统一记录在开发检查文档；实现细节直接查看代码和配置。
