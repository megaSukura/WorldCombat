# P4 计划：机制能力、脚本扩展与样机替换

**状态：P4 功能验收完成，样机退场（2026-09-14）。** 用户完成全部清单，未发现可识别的清单内功能故障；指挥交互、技能动作与表现按[P5 入口要求](P5-entry.md)重新设计。实际结果见 [P4 检查记录](../development/P4-checks.md)。

依据：[完整路线](../../cobblemon_world_combat_plan_v0.3.md#sec-15)、[脚本与机制要求](../../cobblemon_world_combat_plan_v0.3.md#sec-08)、[P3 验收及交接](../development/P3-checks.md)、[原生接入边界](../architecture/cobblemon-integration.md)。

## 目标与交付

按用户 2026-09-13 的补充确认：以原招式名称、介绍、设定和效果为灵感创作新技能，机制与用途服从本项目的世界战斗。P4 建立创作基础；P5 设计正式内容，并按需要补充能力。原生培养复用、全量覆盖与扩展性要求持续有效。

**完成原生接入、机制、操作和表现的可用闭环，并用实际内容替换证明扩展性。** 技能、AI、交互和表现能够独立制作、组合及替换；原生培养、属性、状态、特性与携带物真正影响世界战斗。

本阶段交付两个 Mod 的增量、双层 SDK、可组合的机制与原生规则包、可装卸的验证内容，以及实际检查记录和分组试玩说明。P4 样例服务于能力验证；P5 再逐项设计有充分广度的代表性正式招式、配招和遭遇，P6 串联完整游玩，P7 建立发行维护，P8 全量生产。

已核对[锁定招式基线](../architecture/move-scope.md)：实际数据的 952 个键，经 16 个别名归并后对应运行注册的 936 个招式。继续整理学习、获得、随机调用及特殊系统产生的路径；[需求对应表](../architecture/P4-requirements.md)记录当前事实和待落实事项。条目引用共用机制和检查依据，支持新技能的策略多样性。下表用于归类已知需求，后续发现的能力缺口继续补入对应批次。

| 需求族 | P4 需要具备的表达与执行能力 |
| --- | --- |

| 结算与修正 | 物理／特殊、固定及按生命比例结算、条件击倒、治疗、吸取、反伤、会心；属性、命中／回避、免疫、伤害归因与友敌关系共同参与 |
| 状态与能力改变 | 原生持续状态、临时强化／削弱、速度与行动控制、持续伤害／恢复、属性／特性临时改变；叠加、刷新、到期及离场语义明确 |
| 效果之间的操作 | 解除、延长、传递、复制、反射、重定向、替身承伤和效果链接；内容声明支持的操作及相应处理 |
| 位移与站位 | 原生导航、击退、拉拽、跳跃、冲刺、传送和交换位置；使用当前可用运动方式，服从碰撞、可达性、控制权与权限 |
| 场地与世界交互 | 场地／天气、进入或离开区域触发、陷阱、屏障、可交互构造物、方块／火焰／流体操作；范围、掉落、施工与到期处理受统一约束 |
| 感知与辅助对象 | 视线遮挡、隐藏、声音观察、最后可见位置与记忆；诱饵、替身、召唤和其他临时对象具有可识别的来源及清理归属 |
| 招式与资源变化 | 调用／复制／随机选择招式、变身、招式锁定／封禁、资源变化、主动或强制换入换出、携带物转移及消耗；保留原生身份与唯一结算 |

P4 以原生素材和新玩法设计共同发现能力需求，实现覆盖上述机制族的通用能力和机制库，并以样例验证组合。具体招式的正式设计与选题进入 P5／P8；P4 先完成本批完整体验依赖的能力；其余需求记录归属，在首次用于正式内容前完成实现与检查。

效果协议采用有命名空间和版本的状态、事件与操作，状态可附着于行动者、区域、效果或动作实例。机制库定义提出、拦截、修改、结算、事后通知等阶段和顺序依赖，宿主检查结构、依赖冲突和因果链预算。声明可复制或传递的效果需要提供数据和处理方式；其他效果明确返回支持情况。

持久状态采用可序列化数据和版本迁移，瞬态任务、监听、辅助对象及表现都有所属生命周期。收回、倒下、卸载、换维度、重载及包移除按声明终止、暂停或恢复；时间以逻辑时间处理。世界改动只清理仍由自身拥有的内容，保留玩家后续施工。

## 原生效果与 P3 观察的处理

**原生功能以实际效果闭环验收。** 持续状态与原生恢复／捕捉共用一份原生数据；特性和携带物按内容需要核对素材与原生接口，逐步设计并实现世界战斗效果，包括触发条件、顺序、消耗、抑制、恢复及离场处理。原生世界行为与新战斗共同涉及的效果明确唯一执行入口，共用机制复用检查。

会心与反伤从实际发生的结算结果触发原生成长记录。遭遇开始、结束、换目标、收回、倒下及重入的计数语义由脚本明确，同时衔接特殊球条件；成长写入仍走 P3 的原生入口。

Mega、Z 招式、极巨化、太晶化等，逐项核对锁定版本中的数据、获得／调用入口与附属依赖。P4 给出可验证事实和推荐方案；涉及新增依赖或支持范围的决定集中提交审阅，在首次使用相应系统的正式内容前完成范围决定和实现。完成依据包括实际操作、效果、资源及生命周期。

**移动速度：** 常规移动以原生当前运动能力及行为倍率为基准，脚本选择跟随／追击策略并叠加速度效果。原生六维中的速度、世界移动速度和动作时序分别定义映射，采用可调整的脚本规则，并验证培养／状态变化的实际作用。技能位移按自身机制请求通用运动操作。

**多伙伴：** 每只纳入世界战斗管理的伙伴独立持有持续意图、授权与动作状态；选择操作改变当前指挥对象和 HUD。切换选择后，其他受管理伙伴继续执行自己的有效安排；自由活动只释放对应伙伴的持续 AI，手动动作完成后交回原生行为。收回、PC、交换、骑乘、休息和进化继续遵守原生交接约定。

P4 使用两只同时放出的伙伴验证上述分离。自动纳入方式、出战上限和切换规则放在玩法配置与脚本中，随本批给出可调整默认值；两只作为验收规模，核心支持按配置管理多个行动者。

## AI、交互与表现的可用标准

AI 通过有限范围的观察读取事实，由脚本组织记忆、目标与计划。机制包可提供使用条件、成本、风险、预期结果和候选参数，预测使用只读快照及有界工作。手动与自主行动共用合法性、资源和执行路径，临时技能结束后恢复有效意图；失路、失去目标和授权范围变化都有可理解的处理。

复杂输入覆盖多对象、多步骤、路径、已有场地效果的选择，以及开始／持续更新／停止。参数具有结构版本，服务端复核权限、对象及交互阶段；AI 能直接生成同样的参数。预览、真实蓄力和持续引导分别管理，沿用统一确认、取消、失焦和输入释放习惯。

客户端脚本组合轨迹、光束、范围、声音、状态标记与粒子，宿主批量执行表现。双方按已安装内容包的协议版本交换结构化数据；服务端提供权威几何、动作阶段和持续效果状态，客户端按当前快照更新表现，处理中途加入、重连和结束；P4 使用有界完整快照，增量优化随实际规模安排。低画质优先保留范围、时机和必要状态信息。

G 面板在 P4 改到便于操作和辨认：清楚显示当前指挥伙伴、持续意图、授权及失败原因，常用指令减少翻找，使用统一基础视觉样式。完整队伍管理和最终视觉打磨由 P6 结合正式内容完成。

## 怎样证明能够扩展和删除样例

先将现有防护、岩障、移动等样机整理成可装卸的验证包，并分离原生基础规则与测试场景。随后用导电包组合潮湿、电荷、绝缘和传播，接入 AI 候选及电弧表现；在可用 SDK 上再加入声音诱导包，以声音观察、短时记忆和诱饵选择验证另一条扩展路径。

最终执行以下实测：

1. **移除旧样例。** 在测试配置中移除 P1–P3 样例技能、AI 和表现包及旧测试 UI 入口，清理它们的注册、监听、任务和临时对象；基础接入及原生操作继续可用。
2. **装入替代内容。** 保持两个 Mod 产物不变，仅安装新的内容脚本、交互与表现资源，实际执行新技能和 AI；验证旧样例的玩法分支已迁出宿主实现。
3. **检查组合。** 用导电与既有接触语义、声音诱导与既有感知／意图组合；新包提供对应协议和候选，组合结果有明确依据。
4. **检查独立与存储。** 无 Cobblemon 环境运行通用技能与 AI；完整组合中验证一个自定义持久状态的真实保存／重启、版本迁移及包移除处理，保留原生个体数据。

遇到确实缺少的底层能力时补充通用接口并记录理由，随后重新进行内容扩展检查。SDK 持续随真实需求修正。

制作工具只补当前所需：内容包标识／版本／依赖、分包构建与安装、结构和资源引用校验、源码错误定位、实例及残留计数。新增普通机制通过内容包接入；维护边界重载时先清理瞬态内容，新包验证通过后启用，加载失败则保持受影响内容停用并报告原因。

## 检查与人工参与

Codex 按批次完成构建、类型与协议检查、相关规则／隐藏专服验证。重点覆盖效果顺序及反应链、资源唯一结算、原生状态一致性、控制交接、持久化、内容替换和清理；公共生命周期改动时扩大到受影响的 P1–P3 代表路径。运行一个代表场景观察耗时和残留，规模测试随实际使用需要安排。

人工试玩建议合并为三组，可在方便时连续完成：

| 试玩组 | 用户需要观察的结果 |
| --- | --- |
| 原生效果与移动 | 培养、状态、特性和携带物实际生效；恢复与捕捉一致；跟随／追击和速度效果可理解 |
| 多伙伴与复杂操作 | 两只伙伴保持各自意图；切换指挥、自由活动与原生行为交接清楚；多步骤选择、引导、取消和挖建共存；G 面板易操作 |
| 机制组合与表现 | 导电、诱导、反射／传递及场地样例的结果可读；AI 能使用新机制；低画质保留必要提示；保存重入符合各类状态约定 |

每组就绪后提供可运行版本、测试存档或副本及简短步骤。可见启动前按[协作规则](../../AGENTS.md)说明窗口数量、预计时长和人工参与，再按用户确认的时机启动；用户自行逐组反馈。等待期间继续独立开发，运行中的游戏由用户安排保存和退出。

网络请求、快照及专服加载随本阶段检查。首次联机使用前，按总计划 T05 在真实专服和至少两个客户端上观察施法、持续效果、加入与重连；尚未进行时明确记为待联机实测，继续不依赖该结论的工作。

## 完成条件与进入 P5

1. 原生数据归属、当前世界语义及重要机制形成可用闭环；剩余能力明确归属，在 P5/P6 具体设计需要时补齐，P8 前复核共性缺口。
2. 技能、机制、AI、交互及表现的具体规则由内容脚本承担；核心保持独立，原生事实和写入留在领域适配。
3. 旧样例移除、新包安装、跨机制组合、核心独立运行及自定义状态保存／迁移均有实际结果。
4. 取得移动速度、多伙伴接管、复杂操作和表现的人工结果。2026-09-14 已完成清单；用户决定旧交互与样例表现退场，其正式可用性在 P5 首批内容中重新验收。
5. 交付可运行产物、实际检查记录和 P5 可使用的机制依据。完整玩法打磨、首次联机前的实测及长期体验按路线继续推进，并明确各自状态。

满足上述条件后，提交 P5 代表性正式内容计划供审阅，以 40–60 招作为选题起点，根据机制与组合覆盖确定具体名单。
