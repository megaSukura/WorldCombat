# 体验反馈与有限范围改进

目标是在有限成本内改善实际游玩的体验。内容覆盖规模与体验成熟程度分别记录；用户可以只反馈正常游玩接触到的部分，已有交付与验证结果作为后续工作的基础。

## 反馈与本轮范围

一次战斗、一套配招、几段说明或几招的对比，都可以成为完整的反馈情境。反馈包括功能错误、操作体验、文字的 AI 味与可读性、视觉、创意，以及并行创作带来的同质化、功能重叠和效果相互覆盖。用户提供感受、原文、截图或发生过程即可，技术归因由协调者负责。

协调者区分反馈对象、证据支持的结论和实际修改范围。每轮明确三件事：具体问题是什么、本轮改善哪些地方、在原情境里预期看到什么变化。根据收益与当前时间成本，选择能产生可观察改善的小范围改动。

相似现象提供调查线索；扩大修改或回归范围，需要共同根因、实际调用影响及成本依据。局部反馈的结论保留在其证据范围内。全量修改与全量验证按实际必要性单独决定。

## 按根因选择修改位置

| 反馈 | 优先处理位置 |
| --- | --- |
| 说明空泛、有 AI 味、读不懂 | 对应文字及其描述的真实行为 |
| 某招节奏乏味、创意没有展开 | 该招的关键过程 |
| 几招同质化或功能重叠 | 实际一起使用、比较的那一小组，明确各自用途与区别 |
| 某招视觉与判定不一致 | 该招的机制参数、表现载荷及客户端消费者 |
| 多个效果互相覆盖 | 相关单元的注册身份、叠加关系与生命周期 |
| 不同内容出现同一种通用错误 | 核实共同原因后，修正对应共享契约或实现 |

共享修改应能说明通用行为哪里有误、正确契约是什么、哪些调用者受影响，并用相应技术检查验证。通用的事实、操作、策略与生命周期由共享层提供；具体文案、节奏、视觉编排和玩法取舍由内容单元定义。以这种职责划分判断修复位置，避免为个别内容在内核堆积特殊分支。

## 主观体验与经验复用

文字、视觉、创意和区分度通过少量前后对比收敛：先改用户指出的具体内容，再在原使用情境中判断改善。用户认可的正式内容，按其认可范围成为后续修改和创作的参考，遵循项目的范本验收约定。

一次局部认可可以形成有具体实例支撑的偏好，相关内容在后续实际修改时吸收。并行创作的重叠问题优先在真实配招、交战或选择情境中处理，使玩家眼前的选择有意义。

## 验证、收尾与交接

- 技术检查按实际改动及影响范围执行；操作与观感通过对应情境的试玩反馈确认，可见测试遵循 `AGENTS.md`。
- 每轮以本轮目标的完成情况收尾，并说明实际验证和用户认可的范围。成本较高或收益尚不明确的意见可以保留，待相关内容值得投入时再处理。
- 需要委派时，按 `AGENTS.md` 第 7 条选择 Codex 原生子代理或 OpenCode 批量工具。每次交接都提供当前源码入口、原始反馈、限定目标、已核实的接口与证据、验证要求，使接手者能独立完成任务。
- 每轮在 `archive/feedback/` 留一份简短记录，写清原话与情境、本轮范围与预期变化、实际修改与验证、用户认可范围，以及待处理意见和下一步。实现细节链接源码，后续会话据此接手。

协调者负责定位、范围与交接，内容作者负责所分配的修改，集成者负责共享实现和相关技术验证，用户反馈自己实际体验到的部分。
